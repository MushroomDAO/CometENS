# acceptance — 用户视角「算不算做好了」

验收永远从**外部使用者**视角写,不从代码视角写。当前阶段(M1)全部在**测试网**上验收。

## 三类使用者

| 角色 | 是谁 | 他要什么 |
|---|---|---|
| **社区运营者 A(自部署)** | 有技术能力的社区,想完全自己掌控 | 拿到仓库,自己部署一套,管自己的 `xxx.eth` |
| **社区运营者 B(委托托管)** | 没技术能力的社区 | 保留域名所有权,把**管理权**委托给我们代运营 |
| **社区成员 jack** | 普通用户,不懂链 | 加入社区就拿到 `jack.xxx.eth`,并且这名字真归他 |

## 模式 A:自部署(Self-Hosted)

**做好了 = 一个从没见过这个项目的开发者,照着 `docs/SELF-HOSTING.md`,
在 2 小时内用自己的 .eth 测试域名跑通全流程,全程不需要联系我们。**

逐条验收:
1. `pnpm preflight` 能在部署前就报出配置缺失/写错(不是运行时才炸)。
2. 一条命令完成合约部署 + 参数输出:`pnpm bootstrap:community`。
3. 照文档把自己的 Sepolia 测试域名 `setResolver` 后,
   `viem.getEnsAddress('alice.<他的域名>')` 返回正确地址。
4. 全程没有任何一步需要我们的私钥、我们的 Worker、我们的许可。

## 模式 B:委托托管(Delegated)

前提事实(已复核修正):ENS 的**所有权**(谁持有 `xxx.eth`)与**解析去向**可以分离 ——
社区 `setResolver` 指向我们的 Resolver 即完成委托,**所有权始终在社区手里**。

⚠️ **但"撤销"的含义必须说准**。此前写的"一条命令 `removeRegistrar` 即可撤销,
撤销后我们再也发不出新子域"是**错的**:托管场景下合约 owner 是我们,
而 owner 无条件绕过 registrar/quota/expiry 检查(见 architecture.md)。

**做好了 = 社区只做一次 `setResolver`;之后子域分发由我们代跑;
社区随时可通过在 L1 改回自己的 resolver 收回解析去向;
并且我们在文档里如实说清运营方在技术上能做什么、不能做什么。**

逐条验收:
1. 委托生效:社区 `setResolver` 后,`viem.getEnsAddress('alice.<社区域名>')` 正常解析。
2. **撤销可验证(真实机制)**:社区在 L1 把 resolver 改回自己 → 我们这套不再对该域名生效。
3. **信任模型如实披露**:`docs/DELEGATED-HOSTING.md` 必须写明
   ——「已发出的子域,运营方(合约 owner)在技术上有能力覆写记录、转移 NFT;
   这不是 bug 而是运营逃生舱;若不接受,请走模式 A 自部署」。
   文档不得出现"撤销后我们再也发不出子域"这类**当前不成立**的承诺。
4. 若要让 Mode B 的撤销变成链上强约束,需要先做架构决策(见 tasks.md TB.3),
   本轮不擅自决定。

## Mode A 的委托能力(registrar 的真正用武之地)

社区自部署后 owner 是社区自己,此时把日常发放权委托给热钱包(或委托给我们)
才是 registrar + quota + expiry 的正确用法,且 `removeRegistrar` **撤销真实有效**。

验收:授权 → 发放 → 撤销 → 再发放必须 revert(`Unauthorized`),
且必须**同时**有一条测试证明 **owner 不受该撤销影响**(避免把假阳性当成功)。

## 成员 jack 的验收(注意:jack 不注册、不登录)

CometENS 是**大系统里的一个组件**,不承担用户账号体系。目标形态是:jack 不来我们这里"注册",
子域名由**授予**产生,两条授予路径:

| 路径 | 谁触发 | 场景 |
|---|---|---|
| **API 自动授予** | 上游系统调用我们的 API | jack 加入社区 → 上游系统自动为他申领 `jack.xxx.eth` |
| **管理员手动授予** | 社区运营者在管理控制台点一下 | 补发、特批、批量运营 |

**做好了 =**
1. 上游系统一次 API 调用即可为某个地址授予子域,拿到 `{name, node, txHash}`。
2. 管理员在控制台输入「标签 + 目标地址」即可手动授予,有明确的成功/失败反馈。
3. 无论哪条路径,名字**真归 jack**:`subnodeOwner(node)` 是他的地址,他能把 NFT 转走。
4. 任何人(不登录)都能在公开查询页输入名字,看到它解析到哪个地址。

## 界面验收(用户 2026-09 明确要求)

**做好了 = 主干流程的页面看起来像一个产品,不像 demo。**

界面只有两个真正的主干面(不做用户账号体系、不做登录):

| 页面 | 给谁 | 核心动作 |
|---|---|---|
| **管理控制台** | 社区运营者 | 手动授予子域、管理 registrar 授权、查改记录 |
| **公开查询页** | 任何人,免登录 | 输入名字 → 看到解析结果与归属 |

判定标准(可核对,不靠感觉):
1. 存在**统一设计系统**(共享 CSS 变量:配色/间距/字号/圆角/阴影),
   而不是每页各写一段内联 `<style>`。
2. 两个主干面 + 落地页视觉语言一致:同样的按钮、输入框、卡片、状态提示组件。
3. 有真实的**状态反馈**:加载中、成功、失败、空状态都有设计,
   不是 `alert()` 或裸文本。
4. 移动端可用(375px 宽不横向滚动)。
5. 落地页能让一个不懂链的人在 30 秒内说出「这是干嘛的」。

## 明确不在本阶段验收范围

- 主网(Ethereum / OP mainnet)部署 —— 推迟到 M2。
- Web2 域名(DNSSEC → ENS)绑定 —— 增量,M3。
- 计费/付费子域 —— 不做,本项目是数字公共物品。
- **终端用户账号/登录体系 —— 不做**。CometENS 是组件,身份由上游大系统持有。
