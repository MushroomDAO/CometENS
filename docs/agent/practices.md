# practices — 这个仓库怎么干活

> 这些规程**全部来自 2026-09-03/04 这一晚真实犯过的错**,每条都带着当时的读数。
> 抽象规则没人记得住,而带着实例的规则可以被搜到、被复核、被推翻。
>
> **第一人称是刻意的。**「我把它归到了…」是提醒,「不要把它归到…」是训诫 ——
> 对一个不在场的贡献者,后者门槛更高、更容易被略过。

### 合并前协议

*(2026-09-04,一次 preview 变红之后加的)*

**合并前把分支 rebase 到最新集成分支并实跑一遍,即使 GitHub 说没有冲突。**

原因是一个我们真的撞上的失败:`#50` 加了一道守卫禁掉某句被撤回的话,`#48` 的账本里
**解释那句话为什么被撤回时引用了它**。两个 PR 各自在自己分支上都绿,合到一起才红 ——
**任何一方的 review 看自己的 diff 都发现不了**,因为违规内容和守卫分别在两个 PR 里。

「可干净合并」只说明文本不打架,不说明**合并后的仓库仍然成立**。守卫、断言、
从源码推导的清单,都是跨文件的性质,它们只在合并后的那棵树上才有意义。

  git fetch origin && git rebase origin/preview && pnpm test && npx tsc -p tsconfig.json --noEmit

先合的那个 PR 从不含违规内容,后合的那个从不含守卫 —— 这个不对称是这类故障的全部来源。

**同一节里的第二条,来自我自己的一次失误:合并前核对批准的是哪个 commit。**

我合并 `#73` 时用的是 `e7c5393`,而评审的 APPROVE 落在 `39c49cf` —— 差三个文件。
我读的是 `gh pr view --json reviewDecision` 返回的 `APPROVED`,
**那是仓库级摘要,不带 sha**;把它读成「这个 commit 已通过」是用作用域比问题小的证据
回答问题(见下面的〈取证规程〉)。**那个 sha 在同一个会话里早些时候就打印过,
信息在手上没用上** —— 所以这条必须是机械的,不能是「下次记得看」。

那次没出问题的唯一原因是评审恰好在合并前把那三个文件验完了。**运气不是控制手段。**

    pnpm check:approval-sha <PR 号>     # 不一致就退出非零,并列出批准之后改了什么

> ⚠️ 这条本身要在合并前 rebase 之后才完整:FU-9 的账本行写在 `#74` 的分支上,
> 而这段协议写在 `#75` 的分支上。**两个 PR 各自都绿,合并顺序决定谁看得见谁** ——
> 正是本节第一条说的那个不对称。#74 先合,本分支 rebase 后 FU-9 才勾得上。

判据是「**最后一条决定性 review**」而不是「最后一条 APPROVE」:先 approve、后在新 commit
上 request changes,取后者才对。反向也一样 —— 先 request changes、后 approve,就该放行。


两处此前写错了,都是 pr-daemon 指出的:

- **`pnpm vitest run test/unit/` 漏掉整个 e2e + integration(28 文件/600 条 vs 34/644)**,
  而被漏掉的 `e2e/upstream-api.test.ts` 恰好是 #45 那格 CONTRACT INVARIANT 的所在。
  直接写 `pnpm test`,也不会随新增目录过期。
- **原来没有 `git fetch`**。没 fetch 的 rebase 用的是可能已落后的本地跟踪引用 ——
  正是本协议要防的错误,发生在上一层。

**但这条协议现在主要由 CI 执行,而不是由人记得。** `.github/workflows/test.yml` 在
`pull_request` 事件上跑,GitHub 为该事件检出的是 `refs/pull/N/merge` —— **合并结果**,
不是分支头。上面这段留在这里,是为了解释**为什么 CI 必须跑在合并结果上**:
协议解释理由,机器执行时刻。

本地那条命令仍然有用(推之前就知道,不用等 CI),但它回答的只是
「**此刻**把这个分支合到**此刻**的 tip 通不通过」,而这个答案在下一个 PR 合并的瞬间失效。

#### 提前知道用的,不是门禁

下面这段的**唯一价值是速度**:推之前就知道,省一个来回。它**不是**判词。

**唯一可引用的判词是 CI 在 `refs/pull/N/merge` 上的那个 check。** 本地跑出来的绿是一个
**上一秒就可能过期的读数** —— 下一个 PR 合并的瞬间它就不再描述任何现存的树。
风险不在于有人误以为它是门禁,而在于有人会在消息或 PR 描述里写
「我跑过合并前检查,绿的」—— 那句话读起来像结论,实际是个过期读数。

#### ⚠️ 别用 rebase 做这件事 —— 它会作废 review

我第一版协议写的是 `git rebase origin/preview && …`,**那和「合并前先测」是冲突的**:
rebase 改变 sha,而 APPROVE 记在旧 sha 上,于是"照协议做"反而让这个 PR 需要重新评审。
(我们已经为这个吃过一次亏:#38 的 APPROVE 记在 rebase 前的 sha,合进去的那棵树没人批过。)

协议要的是**测合并结果**,不是 rebase。造一次一次性的试合并就够,且不动分支:

  git fetch origin
  git checkout --detach origin/preview
  git merge --no-commit --no-ff origin/<你的分支>
  pnpm test && npx tsc -p tsconfig.json --noEmit
  git merge --abort

**只有真的有冲突时才需要 rebase**,那时 sha 无论如何都要变,重新评审是应付的代价。

### 取证规程

**判据的作用域必须和问题的作用域一样大。**

变异规程管的是「断言写得对不对」。这一条管的是更早一步:**取证的那条命令本身够不够大。**

三次实例,都发生在 2026-09-04 一天之内:

| 我问的问题 | 我用的命令 | 它实际回答的 |
|---|---|---|
| 这个目录里**有没有** submodule | `git ls-files -s contracts/lib \| head -3` | 前三条是什么 |
| 这 113 个类型错误的**根因**是什么 | 看首条报错 | 第一条是什么 |
| **Tests** 这个 workflow 跑了什么 | `gh run list --limit 1` | 最近一条 run 是什么 |

三次都拿到了真实读数,三次都不回答我要问的问题。**「有没有」「根因」「哪一个」都是关于全体的,
而 `head`/首条/`--limit 1` 只能回答关于局部的。**

正确形式往往只多几个字符,却换成了同一问题的全体形式:

  git ls-files -s contracts/lib | awk '{print $1}' | sort | uniq -c
  npx tsc -p tsconfig.json --noEmit 2>&1 | grep -oE "error TS[0-9]+" | sort | uniq -c
  gh run list --json databaseId,workflowName -q '.[] | select(.workflowName=="Tests")'

**这条和「对照挡得住坏仪器,挡不住错推理」是同一族的第三面**:
仪器可以是好的、推理可以是对的,而**取证的口径从一开始就比问题小**。

### 理由要经得起核

结论对、理由错的注释**比没有注释更危险**:它会在相邻情形下把下一个人带偏,
而且因为它"说清了为什么",更容易被信。

实例(2026-09-04,CI 的 Foundry 步骤):我手写安装器失败后写的注释是
「安装器没把 foundryup 放在我假设的位置」—— 读起来像"手写会踩到未知的路径问题"。
**根因是 GitHub runner 设了 `XDG_CONFIG_HOME`,安装器按 XDG 规范放对了,
而我硬编码的路径是错的;`export FOUNDRY_DIR` 一行即可。** 那个问题是已知的、一行宽的。

于是那条注释用一个错的理由支撑了一个对的结论(「保留官方 action」),
而真理由完全是另一件事:**action 还带着版本管理和缓存,手写版静默丢掉了缓存** ——
在它本想改善的那件事上反而更差。

配套的两条,都来自同一晚:

- **「说清不排会怎样」有个前提:那个"会怎样"必须先被验证过。**
  说清了理由的注释更容易被信,所以它错时代价更大。
- **别把一次自己的失误推广成一类做法的风险。**
  我写"永久性破坏"时脑子里是"手写安装脚本是高风险动作",而读数说的是
  "循环写对了,只有一行路径错了"。**从一个样本推广到一类**,是取证规程的反面。

### 判据先约束现在

**一条写下来但没有在当前状态上跑过的判据,和一个没有测试的断言是同一个形状。**
而它更容易骗人:**判据看起来像在约束未来,其实它的第一份工作永远是约束现在。**

实例:我在 #67 给 `tasks.md` 的索引表定了判据「只有名字和一句话,不含任何会漂移成错的
规则内容」—— **而那张表在同一个 PR 里就违反了它**(五行中有三行在复述具体要求)。
是 review 用我自己的判据量出来的,不是我。

**定判据和用判据是两个动作,而我只做了第一个。** 在同一个 PR 里写下判据、
而当前状态就违反它,不是巧合,是这个形状的典型症状。

规程:**写下一条判据之后,当场把它跑在现状上,并把读数贴出来。**
跑不出鉴别力(所有情形同一个答案)的判据,和没写是一样的。

### 路标不是半条规则

给索引、摘要、路标用的自测(比"改了要不要跟着改"更容易当场用):

> **一个人读完这一行,能不能直接照着做一件事?**
> 能 → 它是**半条规则**,危险在于让人**不必**去读那一页;
> 不能 → 它只能把人送到那一页。

反直觉的那一半:**路标"信息量少"不是缺点,是它的工作。**

  旧:量取规程 | 取退出码那一步不许出现管道;钉子还是下界看那个量单不单调
  新:量取规程 | 同一个量,读法不同会得出不同的数

旧的告诉你两条规则,**却没告诉你这条规程是关于什么的**。一个正在量东西的执行者读到旧那行,
会想"管道和单调性我这次都没碰",于是**不去开那一页**;读到新那行,他知道这是关于测量的,
而他正在测量 —— **他会去开。对一个决定"要不要开那一页"的人,新版信息量更高。**

(所以"只留名字"也不行:只有名字,执行者不知道**什么时候**该开。
路由是路标的全部工作,而那一句正好只提供路由。)

### 起名字的时候问一句这个名字承诺了什么

**名字是一份文档里唯一一个没人当成断言的断言。**

来历:评审在 #73 挡下「标题与验收命令范围不一致」——
标题写「覆盖到 `test/ server/ sdk/ workers/`」,验收命令是 `["src","test","server","sdk"]`。
**不一致的那部分恰好是藏过七端点 500 的目录**,于是这条 task 会在 `workers/` 仍未被覆盖的
那天被标 DONE,同类 bug 可以原样再来。

我采纳了、拆出子 task,**然后给子 task 起名叫「把 typecheck 覆盖到 `workers/`」——
而实测下来 `workers/` 里两个文件已经覆盖了一个,它实际只做 gateway 一个文件。**
同一个毛病,同一小时,第二次。

我最初的解读是「还没变成习惯,只是变成了一条我知道的规则」。评审指出可操作的部分在别处:

> **两次违反都发生在"给东西起名字"的时候。名字读起来像描述,不像断言。**
> 写标题时的心理动作是"我在标记这是什么",而不是"我在声称它的范围"。
> 所以这条规程在别处能生效、在标题上失效,不是熟练度问题,
> **是标题这个位置天然不触发"这是一个会被证伪的陈述"这个念头。**

这个诊断比我的好,因为我的没有可操作面 ——「要更熟练」不告诉任何人下次该做什么动作。

**做法**:起名字时(task 标题、检查名、函数名、PR 标题)问一句**这个名字承诺了什么**,
再问**验收命令兑现的是不是同一件事**。两者不一致时改名字,不是改验收命令 ——
验收命令是量出来的,名字是写出来的。

**这条和「取证规程」不是重复。** 取证规程说判据的作用域要和问题一样大;这条说
**那条规则最容易失效的位置是名字**,以及为什么(名字不触发"我在断言"的念头)。
一条给规则,一条给规则的盲区。

(同族的还有 #55「检查名不再自相矛盾」—— 那次也是名字承诺了检查没做的事。
**第三次了,所以它值一节。**)

### 台账:PR 号在标 `PR_OPEN` 的那一刻就写上

格式:`### T1.2.3 标题  \`PR_OPEN (PR #47)\`` → 合并后改成 \`DONE (PR #47)\`。

**不是为了好看,是为了让"哪些 PR_OPEN 其实已经合了"变成一句可执行查询。**

根因(2026-09-04,同一个漂移第二次):`PR_OPEN → DONE` 这一步发生在**合并之后**,
而合并时那个分支已经不在手上 —— 没人会去编辑那个文件。
**而 `→ PR_OPEN` 发生在你刚开完 PR、分支在手、PR 号就在屏幕上的时刻。成本是零。**

对照解释了为什么只有它漂:`BLOCKED` 从不漂,因为它的解除事件**必然伴随一次人的到来**。

> **一个状态漂不漂,看它的解除事件会不会把人带回这个文件。**

有了 PR 号,核对就是一句话:

```bash
grep -oE 'PR_OPEN \(PR #([0-9]+)\)' docs/agent/tasks.md | grep -oE '[0-9]+' \
  | xargs -I{} gh pr view {} --json number,state -q '"#\(.number) \(.state)"'
```

`test/unit/task-ledger.test.ts` 守住"标了 PR_OPEN 就必须带号"。
**它今天是空转的(零个 PR_OPEN)**,所以那一格必失败对照才是它真正的运行。

### 量取规程

*(两条,都来自同一晚重复踩到的)*

**1. 取退出码那一步不许出现管道。** 先跑完、`rc=$?` 存下来,再处理输出。

  ✗  cmd | tail -1 ; echo $?      ← 拿到的是 tail 的退出码
  ✓  cmd >/dev/null 2>&1 ; rc=$? ; echo $rc

今晚踩了三次,每次都读出一个"成功"。这不是记性问题,是**管道让 `$?` 指向了另一个进程**,
而那个进程几乎总是成功的。

**2. 用钉子还是下界,取决于那个量本身单不单调。**

| 量 | 单调? | 形状 | 为什么 |
|---|---|---|---|
| `skipped` | 否 | **钉死** | 多了是有东西停跑,少了是 skipIf 变了或测试被删 —— 两个方向都要有人解释 |
| `total` | 是(只增) | **下界** | 下界接住"测试消失",又不会让每个加测试的 PR 都来改这个数 |

#48 / #56 / #59 各被地板咬过一次,但**那三次的问题不是"用了下界",
是那个量不单调、而且界恰好等于当时取值**。把"地板不好"当成通则会走反 ——
在单调量上,下界才是这个性质的正确形状。

### 变异测试规程

*(FU-3)*

每组变异都必须配一格**不该失败的对照**。

只报「变异全红」是不够的 —— 它和「这套测试恒红」在读数上一模一样。对照要动一个
**与被测性质无关**的东西(比如只改一个间距 token、只加一行普通正文),并断言它**仍然绿**。

同样地(2026-09-04 补,来自 #46):给每个"防止降级"的断言问一句 ——
**它钉的是降级方向还是升级方向?** 名字里带「不会变成 X」的尤其要看 X 是危险值还是安全值。
一个只钉了安全方向的断言为真但无用,**比缺失更糟,因为它看起来像有人想过**。
