# G2.4 — two-chain native result reconciliation (read-only)

**Status:** local offchain evidence cross-check; **not independently verified Ethereum consensus, not current ENS title, not an OP rights grant and not G2.4 acceptance**. The function `reconcileNativeIssueResult({l1Client,opClient,profile})` in `scripts/reconcile-g2-native-result.mjs` cross-checks the [native issuance receipt observer](G2-L1-NATIVE-ISSUANCE-RECEIPT.md) against the [L1 request-bound relay](G2-L1-REQUEST-BOUND-NATIVE-RESULT.md) and [OP provisional inbox](G2-OP-NATIVE-RESULT-INBOX.md).

Provide **two independently selected read-only public RPC clients** (Ethereum Sepolia chain ID 11155111 and OP Sepolia chain ID 11155420). The profile includes all mandatory fields from `observeNativeIssueReceipt`: `chainId`, `issuer`, `issuerCodeHash`, `registryCodeHash`, `wrapperCodeHash`, `parentName`, `childLabel`, `member`, `expiry` as decimal string and `transactionHash`. Additional required fields are `opInbox`, `opInboxCodeHash`, `opTransactionHash`, `opRequester`, `requestNonce` as positive decimal string, `l1Messenger` and `l1MessengerCodeHash`. All expected runtime hashes and deployment identities must be independently pinned; no default chain deployment is invented.

The L1 sample verifies a successful transaction in a numbered block below the sampled finalized RPC head, the issuer/ENSv1 Registry/NameWrapper runtime, `NativeChildIssued`, historical end-of-block owner/fuses/expiry and a real `issueAndRelay` calldata invocation with matching requester/nonce/member/expiry/label. It independently recomputes the versioned request ID and requires exactly one matching `NativeIssueResultSent` in the same L1 receipt and block. It also requires the pinned L1 relay's immutable OP destination, Messenger address/runtime hash, message version and consumed request ID.

The OP sample requires a successful historical transaction invoking the canonical OP Messenger, in a numbered block below the OP finalized RPC head, and the exact pinned Inbox bytecode. It reads the inbox's `parentNode`, `l1ResultEmitter` and `requests(requestId)` at the **end of the OP receipt block** and requires all request fields match, status `OBSERVED` and the L1 source block number. The receipt must contain exactly one `NativeResultObserved` emitted by that Inbox and bound to the request ID, child node, source block, OP transaction hash and block hash. It rereads both chains' source blocks and finalized heads before returning; a mismatch fails closed. Upstream provider errors are sanitized.

**Direct-call restriction:** this observer requires `L1 tx.to == pinned issuer` and `OP tx.to == canonical OP Messenger`. A multisig, router or contract relaying a message may produce a legitimate L1/OP result but fail this narrow observation as `wrong-l1-entrypoint` or `wrong-op-execution`. No fallback can upgrade such a mismatch to success. All L1 native receipt observer failures are surfaced only by their controlled `l1-*` code, never the raw provider exception; other unexpected RPC/ABI failures use `unverifiable-rpc`. This allows a conservative operator to distinguish a stale finalized source from an invalid local request ID without exposing credentials.

On positive correlation the result is **`DUAL_RPC_OBSERVED`**, with evidence level `TWO_FINALIZED_RPC_OBSERVATIONS_ONLY`. Its `ethereumConsensusIndependentlyVerified`, `nativeCurrentAuthorityVerified`, `finalizedL1IssuanceVerifiedOnOP`, `opGrantsNativeRights` and `sovereignReceipt` values are **always false**. A confirmed historical OP callback is not a guarantee of live ownership, OP resolution permissions, or future-message correctness. A missing/reverted/not-finalized OP receipt currently causes a failure, not a claim that a particular message was permanently lost; pending and retry states require a separate durable workflow.

**Important limits:** both clients may be wrong or collude; `finalized` is an RPC-provided label, not a verified Ethereum beacon/finality proof. The OP callback's immediate source may be authenticated by the canonical Messenger in the reviewed Solidity, but the offchain audit cannot infer execution safety from unrelated unpinned upgrades. L1 Messenger `codehash` pins proxy bytecode, not necessarily its upgradable implementation/governance. Explicit archive-capable RPC service may be required for historic blocks. Because both audits use the **end-of-block** state, later transactions in the same block can cause conservative mismatches. A native parent transfer after issuance or a changed resolver/ENSv2 EAC role is outside this historical correlation; use an independently reviewed finalized-state monitor and never use this report alone to authorize new native names or live records.

Only mocked read-only viem clients are used in this PR's tests. No production L1 or OP deployment, real testnet write, cross-domain transaction, consensus proof or G2.4 acceptance is performed.
