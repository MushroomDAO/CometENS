# G2 OP managed issuance adapter — lease enforcement, not native ownership

> Experimental **OP Sepolia local-test component only**. G2.1–G2.9 remain `PENDING`. A short-lived cross-domain snapshot is **MANAGED**, never evidence of current L1 ENS ownership or a native `SOVEREIGN` handoff.

`contracts/src/G2ManagedLeaseIssuer.sol` is a narrowly scoped, non-upgradeable **new root controller for an existing V4 app-layer NFT contract**. It binds an explicitly chosen OP `G2RootCheckpointInbox`, its expected L1 source-adapter identity, and an application V4 instance to identical `parentNode`, OP Sepolia chainId `11155420` and caller-supplied *runtime* codehashes. These are deployment identity pins, **not** proof that the L1 adapter controls the genuine active ENSv2 name. Pin actual `inbox`, `records` and source identities independently; never trust an address from unsigned JSON, a Worker KV row or a website alone.

### Safe handoff into this adapter

1. Deploy a separately reviewed OP V4 instance for one parent, initially controlled by the community's verified wallet, **without trusting the deployer as L1 owner**. Deploy the one-parent inbox and this issuer adapter with bytecode/address pins. No contract in this PR is deployed to OP Sepolia or Ethereum L1.
2. The V4 wallet **explicitly proposes** this adapter as next `rootController`. The **current live inbox controller** must independently call its `acceptControl()` (no permissionless finalization or outside platform caller); it requires a valid OP inbox lease and `pendingController==this`, calls V4 `acceptController()` and verifies itself as new V4 root. This raises V4 `controllerEpoch`, invalidating *all pre-existing direct V4 operator grants*. Only then may the adapter mint through V4.
3. **Never** grant a V4 operator outside the adapter. The adapter has NO V4 `grantOperator` caller method: its internal scoped grants check OP inbox `sourceEpoch`, quota, flags, **the delegate's own expiry** and expiry not past the lease **when granted**. A same-epoch lease renewal cannot extend an earlier delegate expiry. Every `issue` routes through the adapter as the sole V4 root. Revocation is a reduction-only operation, permitted to the cached current controller **or the original grantor recorded for that specific operator**, including after zero-controller freeze/lease expiry. A new grant replaces the old grantor, so a previous controller cannot cancel a new controller's refreshed grant. If the inbox lease expires, source epoch increases, or controller rotates, no old controller/delegate may issue a new V4 NFT through the adapter. The already-issued member's ERC721 token and direct member records remain their own and continue to work even when issuance freezes.

**Threat-test evidence (local Foundry only):** pre-handoff V4 direct operators lose access on controller epoch rotation; a pending adapter with its own V4 operator grant cannot issue before takeover; explicit current-controller handoff is tested with a missing pending proposal and a mocked inconsistent pending view to exercise the adapter's defensive check; same-controller source epoch changes invalidate grants; revoked/exhausted delegates reject; a 600s delegate expires at its precise boundary while the OP inbox lease remains live for 3600s, including after same-epoch renewal (removing the delegate-expiry guard makes both regression tests fail). Hostile operator initial addresses, changed inbox/records runtime codehash, parent/source mismatch and changed chain reject. Expired OP lease freezes controller + operator issue without clawing back member records. Each issuance revalidates the pinned identities and cached OP lease at execution.

### Explicit limitations

- This adapter **does not** send L1 messages, validate live L1 ownership, audit the canonical cross-domain messenger's upgrade admin, prove OP or Ethereum finality, or implement ENS-native member handoff. The separately reviewed [L1 source](G2-LEGACY-L1-CHECKPOINT-SOURCE.md) and [managed relay prototype](G2-LEGACY-L1-MANAGED-RELAY.md) (#142) can prepare and enqueue cross-domain checkpoints on L1, but no production end-to-end deployment, confirmed delivery or finalized proof exists. Message delivery remains demonstrated only through **local Foundry messenger mocks**. An attacker deploying an otherwise identical source with someone else's parent namehash does not gain actual native ENS ownership, but the inbox/adapter deployment can still be fraudulently *configured* without an independent L1 source-ownership verifier.
- L1 ownership can transfer before a revocation message reaches OP. A previously accepted checkpoint can leave old OP-managed issuance enabled for its remaining lease (no more than two hours). Therefore G2.4's strict **transfer-time** acceptance requirement is **still unmet**. See [frozen boundary](G2-L1-TO-OP-AUTHORITY.md) and [release-blocker issue #138](https://github.com/MushroomDAO/CometENS/issues/138). This module must NEVER return `SOVEREIGN`; its immutable flags `sovereignReceipt` and `l1OwnershipVerified` are both `false`.
- This covers **V4 `issue` through this adapter only**. Any future V4 runtime with another externally callable mint/signature/upgrade bypass must be separately audited and re-pinned; `expectedRecordsCodeHash` alone does not certify safe source code. Signed issuance/Worker V4 integration is separately reviewed. EIP-712 member record writes remain independent of this root lease and are not native L1 record proofs.
- The issuer deliberately cannot return control to a deployer or platform emergency key. Incorrectly configured owner/source/expired lease could permanently freeze *future application issuance*; member NFTs remain independent. Changes to community custody, cross-chain finality and native ENS rights require a new reviewed design and user-approved acceptance.

No testnet/mainnet broadcast, npm publish, SDK default-protocol switch, G2 acceptance or G3 activation is authorized by this proposal.
