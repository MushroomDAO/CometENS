# G2.4 — OP-native result observation inbox (local protocol fixture)

**Status:** experimental, Solidity local proof on OP Sepolia chain ID. This contract is **not deployed**, and no corresponding audited L1 message emitter exists yet. It is intentionally limited to *non-authoritative observation*, not ENSv1/ENSv2 native issuance, OP minting, live resolver record control, a verified-finality oracle or a `SOVEREIGN` receipt. Frozen [G2.4](../goal/G2-ACCEPTANCE.md) stays `PENDING`. See [native issuance proof](G2-L1-NATIVE-ATOMIC-ISSUE-PROOF.md), [native receipt observation](G2-L1-NATIVE-ISSUANCE-RECEIPT.md) and the [cross-domain decision](G2-ZK-MERKLE-L1-AUTHORITY-DECISION.md).

## Request first, native operation on L1, provisional OP result

1. **Queue in OP:** `queueIssue(childLabel, member, expiry)` validates one lowercase ASCII-LDH label and computes its `childNode` from the immutable parent; callers cannot supply arbitrary namehashes. It binds `requester = msg.sender` and a monotonic *per-requester* nonce to a versioned EVM hash of `(source/destination chain, L1 result emitter, destination inbox, parent, requester, child, member, expiry, nonce)`. Only the requester may cancel a pending request. A queue entry **is not consent** from the actual current L1 parent controller, grants no OP rights and does not execute issuance. Third parties can submit their own harmless, gas-paid intents; an L1-native authorization check must still reject unauthorized operations.
2. **Native L1 operation (separate work):** the current L1 owner must explicitly authorize the exact ENS operation, and a native contract must check the current ENS registry/wrapper/EAC authority and execute issuance atomically on Ethereum L1. The deployed L1 emitter must bind that completed native operation to the exact OP request ID, nonce, destination and name; **the existing PR #151 `NativeChildIssued` event does not carry these fields**, so it is insufficient by itself for this receiver.
3. **Authenticated OP message:** only `0x4200000000000000000000000000000000000007` on chain 11155420 may call `observeResult`, and its canonical `xDomainMessageSender()` must equal the immutable L1 emitter address pinned at deployment. The message must repeat both chain IDs, source/destination contracts, parent, version, request ID, requester, child, member, expiry, nonce and the positive L1 block number. The inbox checks all against its own immutable `PENDING` record, then consumes it once.
4. **No premature finality:** a canonical L1→OP messenger can deliver an L1 deposit while its source block has not yet finalized. Accordingly the receiver only changes `PENDING → OBSERVED` (provisional); it records a *claimed L1 source block number* but never concludes that Ethereum consensus finalized it. `sovereignReceipt`, `currentL1AuthorityVerified` and `finalizedL1IssuanceVerified` are all fixed `false`, and the contract cannot grant an ENS name, authority, record writer or member token.

**Cancellation caveat:** cancelling an OP intent blocks future acceptance against that particular request ID; it cannot undo a native name already issued on L1. A successful L1 issuance whose OP message is late, cancelled or lost remains genuine on L1. Such cases need a separate per-name L1 observation/reconciliation workflow and explicit UX status, not an OP rollback fiction.

**Delivery ordering:** multiple pending requests have independent ID/nonce slots and may arrive out of order. A duplicate, old, wrong request, wrong chain, wrong parent, wrong version, changed recipient/expiry, wrong messenger or wrong L1 source fails. There is no global sequence that would let a later legitimate issuance permanently invalidate an earlier in-flight observation. A single request ID is observed at most once.

## Remaining production gates

The protocol is **not an end-to-end deployed solution**. Before connecting it to any OP resolver or ENS authority, a separate independently audited L1 result-producing contract must verify native execution-time rights and include request ID + domain binding in the *same transaction* as the native issuance; the L1 canonical messenger must authenticate the emitting contract. A separately proven L1/OP finality observer must reconcile the result and current native ownership. Source upgrades and migration, real ENSv2 EAC permissions, message duplicates and liveness, source-chain reorg, destination transaction inclusion, member-owned resolver writes and denial of stale OP rights require integration tests and explicit acceptance. **Monitor polling or messenger authentication alone cannot close the strict L1-transfer-to-OP race.** No escrow, platform superowner, live testnet write or silent permission downgrade is introduced.
