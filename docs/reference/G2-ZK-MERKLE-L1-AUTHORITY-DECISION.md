# G2.4 research decision — L1 ENS Merkle/ZK proofs and delayed OP activation

**Status (2026-10-22): RESEARCH / G2.4 `PENDING`.** This is a docs-only option analysis, not a verified bridge, deployed circuit, native ENS issuance or `SOVEREIGN` receipt. It does not change the [frozen acceptance requirement](../goal/G2-ACCEPTANCE.md), the [strict transfer-time counterexample](G2-STRICT-TRANSFER-TIME-PROOF.md), or the [managed OP authority design](G2-L1-TO-OP-AUTHORITY.md). No escrow, platform superowner, live chain writes or mutation of another worker's L1 native issuance branch.

## Decision and security boundary

**EIP-1186 storage Merkle proofs and ZK compression are implementable for a *historical* ENS authorization claim at Ethereum block `h`; they cannot prove that authorization is still live at OP execution time.** Even a valid proof of the newest *finalized* L1 block is silent about a later L1 transfer, expiry, re-registration or migration. Longer waiting, a proof-refresh keeper, short lease, timeout, nonce, cancellation window, event scan or optimistic challenge period can reduce the stale-authority window, **not eliminate it**. In particular a valid ZK proof is a more efficient attestation about its stated inputs, not an oracle for post-proof future L1 events.

## Approved architectural direction: L2 request, L1 native decision, OP result mirror

**2026-10-22 user direction:** L1 makes the final native ENS ownership/authorization decision; L2 queues or submits requests, then syncs and applies the authenticated L1 outcome. A queued OP request does not create an ENS-native right. The delayed OP activation described in the next section remains an optional **MANAGED** exploration, not the native issuance design.

1. **Request or skip queue:** bind a request ID to the exact normalized name, parent, operation, intended L1 owner/recipient, calldata hash, domain/chain IDs, expiry and one-time nonce. Present an OP pending state if useful; otherwise let an authorized caller submit directly on L1. A queued request never substitutes for the current native owner's explicit transaction approval or smart-account authorization.
2. **L1 atomic authority and issuance:** the execution contract evaluates all applicable ENSv1 Registry/BaseRegistrar/NameWrapper, or ENSv2 hierarchical registry/EAC/expiry, operator and implementation predicates inside the **same L1 transaction that actually issues or changes the native name**. Callback/reentrancy and approvals must not create a check/use bypass. A previous RPC call, OP checkpoint or old signature is not a current L1 authorization.
3. **Wait only for real requirements:** submit promptly where possible. Distinguish L1 submitted, included but reversible, finalized issuance, OP sync pending and OP sync confirmed. When independently verified finalized L1 evidence is needed, wait for actual finality rather than a fixed 30-minute policy; missing signatures, unresolved ENS version, proof failure or RPC outage leave a request pending/failed, never automatically approved.
4. **Sync authentic outcome:** use a pinned official L1 execution event/receipt together with source authentication, canonical L1 finality and a versioned L1-to-OP message or proven inclusion. Carry source/destination chain and contract IDs, parent/full name, request ID, L1 block hash/number, transaction/log identity, native owner, generation and monotone sequence. Reject duplicates, older messages or wrong origin. OP may mirror completed native ENS rights but cannot independently create new native rights.
5. **Two UI milestones:** L1 finalized means real ENS issuance exists even if OP delivery is delayed; OP synced means the mirror is caught up. An OP relay failure triggers retry/reconciliation without rolling back successful L1 issuance. A historic OP NFT remains an application asset and is never by itself an L1 sovereign receipt.

Proposed states: OP_REQUESTED → L1_AWAITING_CONSENT → L1_SUBMITTED → L1_INCLUDED → L1_FINALIZED → OP_SYNC_PENDING → OP_SYNCED. Before L1 finality, a request can fail, cancel or expire; after L1 finality, OP failure only changes mirror/sync status. Subsequent L1 change moves the displayed observation to STALE or AT_RISK until reconciled. No two-chain atomicity is implied.

### Optional historical proof and delayed managed OP activation

**User-proposed delayed activation is useful as a safety gate for optional OP-only actions, with a defined limit:**

1. **Request at `t0`**: create an OP `PENDING` request with immutable `(sourceChainId, parent, action, intended controller/recipient, destination contract, requestNonce, expiry)`; mint/grant nothing yet. Only the current authorized requester may cancel, while anyone may submit authentic evidence of loss/freeze.
2. **Validation after a configurable waiting/finality window**: authenticate a finalized L1 execution block `h` *after* request submission; verify the complete native ENS permission predicate at `h`; bind proof to this request, code versions and OP destination. The waiting window is a product/operational parameter, **not** a cryptographic safety guarantee. If finality, consensus root or implementation cannot be verified, remain pending or reject; do not silently downgrade to an RPC claim.
3. **Activation**: re-evaluate nonce, epoch, request expiry, age/finality, registry/version, OP controller epoch and any delivered revocation. An OP grant/mint after verification is explicitly `MANAGED_SNAPSHOT` with a bounded lease/authority scope, even if multiple positive proofs were gathered. A new L1 transfer after `h`, before OP activation or use, can still leave OP unaware: **strict G2.4 remains unsatisfied**.
4. **Native rights path**: for creating a *real L1 ENS subname*, let OP prepare/queue intent but execute the authorization and native issuance **atomically in one L1 transaction**, validating the current ENSv1/ENSv2 authority and downstream approval/callback path at execution. Sync its finalized outcome back to OP as an *observation*, with no independent OP-native right to issue. This is a design candidate subject to separate implementation/audit; calling an L1 `view` from a previous transaction or RPC is not atomic.

Example: request at `t0`, prove A owns at L1 block `h` after a 30-minute wait, and activate A at `t1`. If the parent transfers A→B immediately after `h` and before A's OP grant is used, a valid Merkle/ZK proof for `h` can still pass. A longer delay from `t0` does **not** change this. To completely remove the race while allowing freely transferable L1 ownership, forbid independent authority-expanding OP issuance and do it on L1. Alternatively a separately approved L1 custody/transfer interlock could require durable OP freeze acknowledgment *before* native transfer is allowed; that materially changes user ownership semantics, introduces liveness/recovery risks and is **not** approved here.

## L1 Monitor: necessary for convergence, insufficient for instantaneous revocation

**Decision: implement an L1 ENS Monitor + Reconciler as an operational component.** After L1 issuance is mirrored, native ownership, delegation, expiry, registrar, resolver and migration can still change. The monitor improves correct UI, fast synchronization, retry and safety alarms. **It is not a standalone authorization firewall:** an undelivered L1 transfer cannot be noticed synchronously on OP, so no dependent OP path may issue native ENS rights or enlarge stale native authority based on its last mirror.

| Source change on L1 | Monitor and OP mirror reaction | Authoritative enforcement |
| --- | --- | --- |
| Parent holder transfer, operator revoke, controller rotation | Invalidate cached controller/epoch, mark affected OP views stale and pending intents for native reauthorization | Next *native* issuance verifies current L1 holder/roles in the same transaction |
| Parent expiry, grace, re-registration, wrapper/registrar change | Update parent and descendants' risk/validity; stop representing old snapshot as native authority | Native expiry, registrar and wrapper predicate |
| Member subname transfer/expiry | Reconcile native holder/expiry, retain previous OP-owned app records only as historical/app-specific data | L1 member ownership/record writer rules; no platform clawback |
| ENSv2 EAC grant/revoke, root/admin/approval, subregistry, implementation update | Invalidate previous role/version assumptions; refresh ancestry and per-name evidence; handle changed token IDs | Real current EAC resources and permissions on L1 |
| Resolver writer change or ENSv1→ENSv2 migration | Invalidate old source-version proof; update resolver and migration display; re-evaluate affected children | Native registry/resolver permissions and migration state |
| Source reorg, missed event, bridge delay, watcher outage | Mark unknown/stale, replay from finalized checkpoint, retry authenticated delivery | Valid L1 native result remains authoritative even when OP is behind |

**Monitor design contract (for a separately reviewed implementation):**

1. **Event-driven observation plus state reconciliation.** Watch only version-pinned official ENSv1 Registry, BaseRegistrar, NameWrapper and resolver, or ENSv2 Permissioned Registry, EAC, registrar, migration and upgrade contracts. Inspect their verified ABIs before selecting event signatures. Events trigger a read of the *whole affected authority predicate* at a pinned canonical L1 block; do not infer all permissions from one event. Expiry may happen with no event, requiring periodic state reads.
2. **Finality and durability.** Persist source chain, block number/hash, transaction hash, log index, contract version, parent/name ID, sequence/epoch, and cursor. Process finalized blocks in order, backfill from a durable last-processed point with overlap on restart, verify block hash continuity and reorg handling, and only advance cursor after durable apply. Support multiple registrations, A→B→A, changed versions, skipped blocks, duplicates and out-of-order delivery.
3. **Authenticated delivery.** An untrusted watcher may trigger reads and retry relays; a Worker signature or RPC event claim cannot create authority. OP only trusts an approved, pinned L1 producer through the canonical messenger or an independently validated canonical-state proof. Reject wrong chain/source/version/name/epoch/sequence and replay. A missing update never authorizes a privilege expansion.
4. **Health and freshness.** Show last finalized L1 block examined, last L1 block used for this name, last mirrored OP block, sync status, lag and last error. Process new finalized events promptly; periodically reconcile monitored names and expiry timers. Configure latency targets from actual RPC/finality/bridge measurements; no polling interval gives *instantaneous* transfer-time OP revocation.
5. **Rights boundary.** UI/status sync may lag. Any OP action that can *actually affect live ENS name/record control* is security-critical and must be redesigned around L1 execution-time authority or independently verified equivalent guarantees. Preserve legitimate member-controlled OP application records; label them separately from native ENS resolution and ownership. If the L1-connected resolver treats OP data as authoritative, an old OP writer could still affect resolution even without minting, so record-writer authorization needs its own L1-coupled design and tests.

**Required failure demonstrations:** L1 A→B transfer before watcher delivery; revocation with delayed older positive checkpoint; ENSv2 EAC role grant that rotates a token ID; expiry without an event; resolver swap; v1→v2 migration; watcher offline and cursor backfill; source provider disagreement/reorg; message replay/reordering; and native issuance succeeding on L1 but OP mirroring late. Assert native old-A issuance is denied at its L1 execution, while OP displays stale state honestly and eventually converges. Monitor success never closes frozen G2.4 on its own.

## Authenticating a historical L1 claim

1. **Canonical block root**: prove `(L1 chainId, block number, block hash, execution stateRoot, finality status)` against a trustworthy canonical Ethereum consensus anchor. An RPC-supplied `stateRoot` is only a claim. A valid MPT witness checked against an adversary-chosen root proves nothing about Ethereum. OP's L1Block predeploy supplies L1 origin number/hash, **not its execution stateRoot**; a header inclusion/hash check is still required and its available L1 origin is not necessarily finalized. EIP-4788 exposes *beacon block roots*, which require a fork-aware proof from consensus to the target execution payload/header/state root. EIP-2935 is historical *block hashes* only. Every choice must specify the trust/availability/finality assumptions of moving that anchor to OP.
2. **Storage and code integrity**: verify EIP-1186 account-trie inclusion/non-membership under the authenticated `stateRoot` and storage-trie inclusions and relevant zero/non-membership values under the proven account `storageRoot`; verify the requested slot keys and returned decoded values. Pin contract addresses, runtime code hashes and for proxies their implementation/upgrade control. `eth_getProof` gives **storage data**, not a proof that an arbitrary `eth_call` output is correct. Implementation must fully specify mapping/struct slot derivation, code-specific semantics and handling of upgrades.
3. **Actual ENSv1 rights at `h`**: Registry owner versus NameWrapper wrapped holder, `.eth` BaseRegistrar NFT owner/custody/reclaim and *registration* expiry (not the wrapper's grace-period expiry), parent/child NameWrapper `getData` and `ownerOf`, CU/PCC/other fuses and expiry, approvals/operators, resolver and permissions to create the requested subname. Do not mistake Registry's wrapper address for the human controller. A user's signature alone is insufficient. This legacy path is *not* a current ENSv2 Sepolia permission claim.
4. **Actual ENSv2 rights at `h`**: prove the canonical hierarchical registries/subregistry/parent pointers, entry lifecycle (`REGISTERED` versus `RESERVED`), current `eacVersionId`/`tokenVersionId`, expiry/re-registration, account roles, `ROOT_RESOURCE` regular/admin rights and any inherited ERC-1155 operator approvals. Include EAC role assignment or regrant possibilities, `ROLE_SET_PARENT`, relevant registrar/unregister/upgrade roles, resolver per-record writers and proxy admin. Role/resource calculations and storage slots are **implementation- and version-specific**; ENSv1 namehash/NameWrapper slot assumptions cannot substitute. When claiming *absence* of privileged third parties, prove a complete authenticated holder count/enumeration or a separately audited invariant, not only a negative proof for one known address.
5. **Bound evidence to operation**: proof/circuit statement includes `(version, sourceChainId, L1 block hash/height/stateRoot, source ENS implementation and parent identity, evaluated operation/right, controller/caller, native validity and expiry, source epoch, destinationChainId, OP issuer/verifier, action/recipient, nonce, deadline)`. Verify a circuit/verifier public-input layout with implementation-specific native semantics. Monotone checkpoint sequences and OP nonce consumption reject replay and double activation but do **not** prove continuing L1 ownership. Fail closed on unrecognized ENS upgrade/migration, stale canonical root, mismatched chains, proxy, ancestry or unsupported rights.

**A Merkle allowlist from a Worker proves membership in that Worker's list only.** A receipt/event trie inclusion proves an event occurred, not that *no later transfer event* occurred. An event scan without canonical complete chain history, verified no-gap handling and authoritative state is still not a proof of current native rights. Verification performed solely offchain is an offchain policy; a contract must actually enforce the claimed proof to make it a contract guarantee.

## Implementability and decision matrix

| Candidate | What is honestly established | Main dependency / cost | Strict G2.4 transfer-time outcome |
| --- | --- | --- | --- |
| Signed Worker claim / custom Merkle allowlist | Publisher said A was owner | Trusted signer/root builder | **FAIL** — not independent L1 evidence |
| EIP-1186 MPT + authenticated canonical L1 execution header | Exact ENS slots and authorized predicate at `h` | Root relay/finality, MPT gas, ENS layout and version-specific verifier | **FAIL** for transfers after `h`; may be `MANAGED_SNAPSHOT` |
| ZK proof wrapping MPT + full ENS predicate | Succinct historical predicate at `h` | Circuit audit, verifier key/version, prover availability, L1 root anchor | **FAIL** for transfers after `h`; improves proof cost/privacy, not freshness |
| Authenticated L1→OP checkpoint / short lease | Bind/ownership at an earlier L1 transaction | Messenger upgrades, async delivery, unexpired stale lease | **FAIL** until freeze arrives or lease expires |
| Delayed request→finalized L1 proof→OP activation | No new OP privilege while pending, proven snapshot before activation | Delay UX, source root/finality, another transfer before/after `h` | **FAIL**, but a useful `MANAGED` risk reduction |
| L1 execution-time native authorization and issuance, then OP mirror | Current native rights checked during L1 transaction | Gas; native ENSv1/v2 and callbacks; OP mirror is informational | **Candidate for strictly native L1 issuance only** |
| L1 event monitor + finalized-state reconciler | OP replica converges to an observed native state with lag and recovery | Indexer/cursor, reorg handling, chain/RPC finality, authenticated delivery | **FAIL as a sole gate**; recommended companion for native-first architecture |
| L1 custody or owner-approved transfer/freeze interlock | Cross-domain transfer cannot bypass acknowledged OP freeze *if completely enforced* | Custody, recovery, liveness, new ownership trade-off | **Conditional candidate** requiring explicit decision and independent review |

## Attack/negative-test matrix for any future prototype

| Attack | Negative test and expected evidence |
| --- | --- |
| `h` shows A as holder, then L1 transfers to B without OP notification | Reuse legitimate proof for `h`: old A can still pass an unexpired historical OP gate; **report the counterexample and G2.4 FAIL**, not an optimistic passing test |
| Delay window ends, prove A at `h`, B receives transfer immediately after `h`, A activates at OP | Show that pending/finality checking alone cannot detect B; do not label this strict transfer safety |
| Fake state root, invalid account/storage witness, zero-value/absence forgery | Reject all, including valid trie proof under attacker-supplied root |
| Canonical-looking unfinalized/fork header; OP unsafe origin; wrong L1/OP chain | Reject on chain, canonicality, finality or source-version mismatch |
| Reuse `(proof, nonce)` on a new parent, chain, recipient, issuer or implementation | Enforce signed/proved public-input bindings and consume nonce once; reject replay |
| ENSv1 Registry reports Wrapper but wrapped holder differs, registrar grace, expired parent, approved manager remains | Deny positive authorization unless entire ENSv1 native predicate holds; test registrar versus wrapper expiry distinctly |
| ENSv2 EAC root/admin regrants revoked registrar right, inherited approval or registry upgrade changes semantics | Deny sovereignty or rights invariants lacking proven closure; invalidate version/circuit on upgrade/migration |
| Delayed freeze/relay, relayer censorship or prover outage | Privilege-expanding OP activation rejects if no timely authenticated evidence; member-owned records/revocations remain available |
| Old proof from before ENSv1→ENSv2 migration or expiry/re-registration | Reject source/version/epoch mismatch when known; **record transfer-time gap when unknown** |
| L1 native executor checks at request time but calls issuance after holder transfer; authorization changes inside callback | Re-check in the *same L1 transaction* before issuance with reentrancy/approval/callback safeguards; test old holder reverts and current authorized holder succeeds |
| User sees L1 final receipt but OP relay fails or is delayed | Keep truthful native L1 success and OP_SYNC_PENDING; retry from pinned receipt without duplicate OP activation |
| Watcher misses L1 transfer, domain expiry emits no event, then old OP mirror is used | Monitor backfill eventually updates display; independent OP expansion or resolver-write authorization must be blocked by protocol design even before notification |

## Proposed next increment (separate PRs, no change to frozen G2.4)

1. **Selected flow specification/fixture:** model `OP_REQUESTED → L1_AWAITING_CONSENT → L1_SUBMITTED → L1_INCLUDED → L1_FINALIZED → OP_SYNC_PENDING → OP_SYNCED`, and `STALE/AT_RISK` after later changes. Pin request ID, native execution and chain receipt, source finality, relay version and duplicate handling. Keep optional `PENDING → EVIDENCE_VERIFIED → MANAGED_ACTIVE` tests to show the *post-proof transfer failure*, not as native issuance authorization. No live network writes.
2. **Independent proof feasibility spike:** fixed legacy ENSv1 codehash/storage layout, fixed finalized L1 header in a local fixture; verify EIP-1186 account/storage MPT and attack cases; measure gas. Then assess ENSv2 as a distinct, version-pinned circuit after independent review of real EAC/storage semantics. This is **not** a permission to deploy or upgrade live contracts.
3. **Separate native-issuance implementation:** [PR #151](https://github.com/MushroomDAO/CometENS/pull/151) develops the L1 execution-time issuance/guard prototype, subject to its own review and acceptance. An L1 guard must validate *every actual privilege-expanding native action* and give the OP side no independent native issuance claim.
4. **Independent monitor work package:** version-pinned ENSv1/v2 source/event map, finalized cursor, state reconciliation (including expiry without events), authenticated source/destination relay, OP stale status and convergence metrics. Add simulations of L1 A→B with delayed delivery, missing/forked events, offline backfill and ENSv2 upgrades. Monitor cannot be accepted as the G2.4 revocation safety mechanism alone.
5. **Release gate:** `G2.4` can be accepted only after an independently reviewed implementation proves transfer/expiry/re-registration/migration cannot expand former privileges at the time relevant rights are exercised, including delayed proof and OP relay race cases. If it cannot, explicitly retain `PENDING`; `MANAGED_SNAPSHOT` is never an L1 native `SOVEREIGN` proof.
