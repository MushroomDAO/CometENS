# 委托托管:你交出了什么,保留了什么

> 面向**考虑把域名管理委托给运营方的社区**。
> 如果你有技术能力自己跑,看 [SELF-HOSTING.md](SELF-HOSTING.md) —— 那条路你不需要信任任何人。
> 当前仅测试网。

## 一句话

**域名所有权始终是你的;解析去向和子域发放交给运营方代跑。你随时能收回解析去向。
但已经发出去的子域,运营方在技术上仍能覆写和收回。**

最后半句是这份文档存在的理由。如果你不接受它,请走自部署。

---

## 你交出的和保留的

| | 谁掌握 | 你能单方面改吗 |
|---|---|---|
| `你的社区.eth` 的 ENS 所有权 | **你** | ✅ 是 |
| 该名字的 resolver 指向 | **你**(在 L1 设置) | ✅ 是 —— 这是你的收回开关 |
| L2 上发放子域、写记录 | 运营方 | ❌ 否 |
| 已发出子域的 ERC-721 归属 | 各自的持有者 | ❌ 否(但见下) |

委托只有一个动作:在 Ethereum 上把 `你的社区.eth` 的 resolver 指向运营方的 Resolver 合约。
**没有别的授权,没有代币批准,没有把域名转给谁。**

## 怎么收回

在 L1 把 resolver 改回你自己的(或任何别的)。**立刻生效,不需要运营方配合、不需要通知谁。**

```
你 → ENS Registry.setResolver(namehash("你的社区.eth"), <你选的 resolver>)
```

之后 `alice.你的社区.eth` 不再经过运营方的链路。已经在 L2 上的记录还在那个合约里,
但没有人再从那里读它们了。

**这一条实测过,不是设计意图。** 2026-09-04 在 Sepolia 上把 `aastar.eth` 的 resolver
清成 `0x0`,子名的 `OffchainLookup` 立刻不再触发;改回后恢复。两笔交易可查:
[撤销](https://sepolia.etherscan.io/tx/0xf0d556f9f324ef210f9d77789c9ab4f5d6f898e1e3a3b4aab6227b2f5d2bc4b6) ·
[恢复](https://sepolia.etherscan.io/tx/0x2bf77cd451257742eb33b47252c5c22b92253e74b99116fdaae7b8ce54d3ea83)。
自己复核用 `pnpm verify:b2 --root <你的域名> --execute`。

### 🔴 但先确认一件事:你在 L1 上**有没有一个属于你的节点**

同一次实测里,先撤的是 `forest.aastar.eth` —— **没有效果**,子名仍然走运营方的链路。
我最初把原因写成「ENS 通配解析往上走,所以清自己那一层撤不掉」。
**结论对了,理由只对一半,而照那个理由给的处方是错的。**(PR#104 评审在祖父已清零的
同一个区块上做了对照,把这一点钉死了。)

真正的规则是两条:

- **清成 `0x0` = 把控制权交上去。** 该层没有 resolver 了,解析继续往上找,
  落到第一个持有 resolver 的祖先 —— 如果那是运营方,你等于什么都没做。
- **改指到你自己的 resolver = 把控制权拿回来。** 实测:在 `aastar.eth` 已被清零的那个区块,
  `alice.forest.aastar.eth` 仍然走运营方路径,**正是因为 `forest.aastar.eth` 自己还指着运营方**。
  它那一层是有效的,只是指错了地方。

所以决定权不在「往上走」这个规则,在**你手上有没有那个 L1 节点**:

| 你的情形 | 你该做什么 |
|---|---|
| 你拥有自己的 `.eth`(`你的社区.eth`) | `setResolver(你的社区.eth, 你的 resolver)` ✅ |
| 运营方给了你一个**你自己拥有**的 L1 子节点(如 `你的社区.运营方.eth`) | 同样 `setResolver(<那个节点>, 你的 resolver)` ✅ —— **不要设成 `0x0`**,那是把控制权交回给运营方 |
| 你的名字是**纯 offchain 通配**(L1 上 `owner` 和 `resolver` 都是 `0x0`) | ❌ **没有可改的东西** |

第三行是本服务默认发名的形态:实测 `alice.aastar.eth` 的 `owner` 和 `resolver` **都是 `0x0`**
—— 它在 L1 上**根本不存在**,只是运营方 resolver 的一条通配解析。
**不是「清了没用」,是「没有可清的东西」。**

**结论对社区只有一句话**:要「随时能自己走人」,你必须在 L1 上真的持有一个节点 ——
自己的 `.eth`,或者运营方**把子节点的 owner 转给你**。
拿到的只是一条通配解析,那么退出与否由运营方决定,**而这不是承诺问题,是 ENS 解析规则**。

**给运营方的对应义务**:如果你声称提供退出权,就要在发名时把 L1 子节点的 owner 转给对方,
而不是只给一条通配记录。`pnpm verify:b2 --root <名字> --execute` 能让对方自己验这一条 ——
**它是不是真的有效,取决于上表你落在哪一行。**

> ⚠️ **收回解析 ≠ 收回已发出的名字。** 见下一节。

## 运营方技术上能做什么(必须读)

这不是"理论上的风险",是 `L2RecordsV3` 明确写着并且有测试背书的行为:合约 owner
**无条件绕过** registrar 允许列表、配额和到期时间。托管模式下运营方就是 owner。

具体地,运营方可以:

1. **在你的 parentNode 下发放任何子域**,即使某个 registrar 已被撤销、配额已耗尽;
2. **覆写任何子域的记录**(addr / text / contenthash),包括不属于他的;
3. **把任何子域的 ERC-721 转给别人**,不需要持有者同意
   (`transferSubnodeByGateway` 是 `onlyOwner`,链上没有签名校验)。

三条各有测试钉住:`contracts/test/L2RecordsV3.t.sol::test_ownerCanStillRegisterAfterRevoke`
和 `test_ownerBypassesRegistrarQuota`。评审时把这三处逃生舱逐个从合约里拆掉,该测试都会转红
—— 所以这不是"文档这么写",是被验证过的性质。

4. **改任意地址的反向解析**(`setPrimaryNode`,`L2RecordsV3.sol:237`,`onlyOwner`)。

**API 层确实做了 EIP-712 验签和链上归属校验**,日常路径是安全的。但那是 off-chain 约束:
持有 owner 私钥的人可以绕开整个 Worker 直接发交易。

### 还有一条性质不同的:失败原因你看不到,运营方看得到

上面四条是「运营方能对你做什么」。这一条不是能力,是**条件**:
出问题的时候,**能看见原因的人不是要排查的那个人**。

**分开写不是为了分类整齐,是因为上面那份清单的可信度来自"每条都能被拆开验"** ——
拆掉合约里的逃生舱,对应的测试就转红。这一条**没有测试,而且不可能有**:
它是「进程跑在谁的账户里」的性质,不是代码的性质。把一条不可证伪的陈述放进那份清单,
等于让它白拿那份可信度,**而代价是你从此分不清哪几条是被验过的**。

判据很简单 —— **这件事要发生,运营方需要动手吗?**

| | 需要他动手? | 你要问自己的问题 |
|---|---|---|
| 覆写记录 / 收回 NFT / 绕过 registrar | 是 | **我信不信他不做** |
| 你看不到失败原因 | **否,他什么都不做也成立** | **我能不能在这个条件下工作** |

两个问题导向两个不同的决定,所以不该混在一张表里。

证明模式生成失败时(`workers/gateway/src/index.ts:596`),三方拿到的东西不一样:

| | 拿到什么 |
|---|---|
| 查询者(任何人) | `Proof generation failed` —— 通用错误,刻意不带原因 |
| **运营方(host)** | **完整原因**,写在 Cloudflare Worker 日志里 |
| **你(委托方)** | **什么都没有** —— 而你才是那个"我的名字解析不了"要去查的人 |

原因不外露是**故意的,而且必须如此**:`#30` 就是从响应体漏出去的 —— 一条上游错误
字符串裹着 RPC provider key,返回给匿名调用者。所以这不是可以简单"打开"的东西。

但代价要说清楚:**worker 日志落在运营方的 Cloudflare 账户里,而运营方 ≠ 你。**
自部署模式下这一条不存在(那个账户就是你的)。托管模式下它给信任面加了一项:
**排查你自己的解析,要经过运营方。**

**如果你需要**:让运营方在响应体里带一个**不透明 id**、日志里写 id + 原因。
你拿到的是一个**可以向运营方引用的凭据**,而不是原因本身 —— 泄露面没变,
而"要不要给你看"从一个技术问题变回一个运营问题。这一步没有做,
因为它该由第一个真实的委托方来定形状,而不是由我们预先猜。

### 还有一条性质不同的:让任何名字解析到任何地址

上面四条要的是 **owner 私钥**(文档说它该冷存)。这一条不同 —— 它要的是**网关签名钥**,
也就是那把 **7×24 在线**的钥匙:

> **持有网关签名钥的人,可以让任何名字对任何查询者解析到任何地址。**

原因在合约里:

- `HybridResolver.hybridCallback` 从**应答**里解出模式
  (`(uint8 mode, bytes payload) = abi.decode(response, …)`)——
  **走签名还是走证明,是应答方自己决定的**。所以网关 `/health` 报的 `proofMode: true`
  是网关侧的偏好,**不是合约侧的约束**;一个不老实的应答方永远选签名模式即可。
- `_verifySignature` 只校验 `signers[recovered]`,签名绑定的是
  `address(this) / expires / keccak(data) / keccak(result)` ——
  **`result` 里是什么,它不检查**,也不与 L2 上的实际记录交叉核对。

这条与前四条的区别值得说清楚:

| | owner 私钥那四条 | 网关签名钥这一条 |
|---|---|---|
| 用的是哪把钥匙 | owner(应冷存) | 网关签名钥(**7×24 在线**) |
| 链上痕迹 | 有(交易可查) | **没有**(只是一次应答) |
| 影响范围 | 所有人 | **可以只针对某个查询者** |
| proof 模式能挡吗 | 不相关 | **挡不住**(模式由应答方选) |

所以文档里"网关签名钥策略上只允许签应答、永不允许签交易"这句,
**不是一种限制** —— 签应答正是这条能力的全部内容。

我们对这把钥匙能做的收敛是**缩短它的暴露窗口**:它可以热轮换,见
[KEY-ROTATION.md](KEY-ROTATION.md)。但在任一时刻,持有它的人拥有上述能力。

### 一个常见的误解

`removeRegistrar` **不是**你收回运营方权限的手段。它是 `onlyOwner` 的 —— 托管模式下
你不是 owner,你根本调不了它;而运营方就算调了,对他自己也不生效。

`registrar + 配额 + 到期` 这套是**自部署模式**的能力:你自己是 owner 时,把日常发放权
委托给一个热钱包或某个小组,可随时撤销。见 [SELF-HOSTING.md](SELF-HOSTING.md)。

## 运营方这边的密钥架构

(2026-09-03 决策,记录在 `docs/agent/tasks.md` TB.3)

1. **密钥保管走 KMS**,私钥保存在 TEE 内,CometENS 通过 RPC 调用其签名。
2. **三个角色三把独立的钥匙**,各自绑定签名策略:
   - `OWNER_KEY` —— 合约 owner,**冷存,不用于日常写入**
   - `WRITER_KEY` —— 执行 L2 写交易
   - `GATEWAY_SIGNER_KEY` —— 签 CCIP-Read 应答,**策略上只允许签应答,永不允许签交易**
3. **签名器是抽象的**:自部署者用 `env-key`(一个环境变量即可),不被迫依赖 KMS/TEE。

### 但 KMS 不改变上一节的任何一条

这一点必须说清楚,否则容易被"我们用了 TEE"安慰过去:

> **KMS/TEE 解决的是「私钥会不会被偷」,不是「拿着这把钥匙的人被允许做什么」。**
> 哪怕私钥永远锁在 TEE 里、谁都偷不走,运营方的服务仍然可以完全合法地请求 KMS
> 签一笔「把某个子域转走」的交易 —— 因为链上就允许 owner 这么做。

所以本文的信任模型是:**你信任的是运营方这个组织不作恶,而不是一套技术保证。**

### 已经在做的收敛

网关签名钥可以在不重新部署、不需要多签的情况下热轮换
(两个 Resolver 都有 `addSigner`/`removeSigner`),流程见
[KEY-ROTATION.md](KEY-ROTATION.md)。这把 7×24 在线、暴露面最大的钥匙,
是目前已经能单独隔离出来的一把。

**当前状态如实说明**:线上部署的 owner、写入 EOA、网关签名者曾经派生自同一把私钥。
上面的三钥分离是目标状态,不是既成事实。用 `pnpm preflight` 可以查当前部署的实际情况
—— 检查项 3b 会明确告诉你它**验证到了**分离,还是只是**没看到**那几把钥匙。

## 接入流程

1. **你**:在 Ethereum 上把 `你的社区.eth` 的 resolver 指向运营方给你的 Resolver 地址。
2. **运营方**:把 `你的社区.eth` 加进服务端的 `ROOT_DOMAINS`。
3. **验证** —— 而且要用**真正独立**的方式,这一步比看上去讲究。

   ⚠️ **换一个 ENS 客户端是不够的。** 任何客户端做 CCIP-Read 都会去 `gatewayUrl` 取应答,
   仍然经过运营方的**网关**,拿到的是同一个(按上一节,可能被伪造的)答案。
   绕开前端不等于绕开网关。

   **真正独立的验证是直接读 L2 合约,再和解析结果比对**:

   ```
   pnpm check:chain                                   # 合约与 owner
   cast call <L2Records> 'subnodeOwner(bytes32)(address)' <namehash> --rpc-url <OP RPC>
   ```

   两者不一致,说明解析路径上有人在给你不同的答案。

   本仓库的端到端脚本也可以跑,但它走的是网关,所以它验证的是"链路通",不是"答案真":

   ```
   bash scripts/resolve-testnet.sh alice.你的社区.eth
   ```

   > 这里给的是 `.sh` 而不是 `.ts`:直接跑 `.ts` 依赖 Node 版本的类型剥离能力,
   > 而 tsx 不是本仓库的依赖。
4. **发放**:走 [UPSTREAM-API.md](UPSTREAM-API.md) 的 API,或让运营方在管理控制台手动发。

## 退出流程

1. 在 L1 把 resolver 改走(立刻生效)。
2. 需要的话,让运营方导出 L2 上的记录 —— 那些数据在链上是公开的,你自己也能读。
3. **已发出的子域仍然记在那个合约里,归各自的持有者。** 换到新的部署意味着这些名字
   需要在新合约上重新发放,旧的 NFT 不会自动跟过去。这一点在决定委托之前就该想清楚。

## 我们不承诺的

- 不承诺 SLA、不承诺可用性
- 不收费,也不因此承担商业责任
- **不承诺"运营方无法动你的名字"** —— 见上文,那不是真的

## 运营方必须做的密钥分离

托管模式下你持有的是**别人社区的名字**,所以「一把钥匙干三件事」在这里不是可接受的起点。

| 角色 | 变量 | 泄露的后果 |
|---|---|---|
| writer | `WRITER_KEY` | 能以运营方身份写 L2 记录 |
| gateway signer | `GATEWAY_SIGNER_KEY` | **能让任何名字对任何查询者解析到任何地址**,链上无痕迹 |
| owner | `OWNER_KEY` | 能覆写记录、收回 NFT、改 registrar |

三者用同一把钥匙,意味着**一次泄露同时具备上面三种能力**。

```bash
PREFLIGHT_KEY_SEPARATION=strict pnpm preflight
```

这会把 check 3b 从 WARN 升级为 **FAIL** —— 自部署允许从一把钥匙起步(那是社区自己的名字、自己的风险),托管不允许。

**设置密钥时只设一个名字**。新旧两个名字都设、且值不同,workers 会**拒绝启动**:
rename 之后哪个名字生效变了,照旧部署会静默换掉签名者 —— 而 gateway 那一格换掉之后,
解析全网失败,部署侧却毫无报错(`/health` 不签名,健康检查照绿)。
