## G2 的工作顺序

| 顺序 | 已有基础 | 下一份可验收交付 |
|---|---|---|
| 1 · G2.1、.2、.5 | V4 per-parent controller、限权 operator、SDK 与 CLI | 固定测试部署和真实 owner 身份，从 CLI 完成跨根隔离、grant、revoke、rotate，记录 finalized 交易与事件 |
| 2 · G2.6 | 合约支持签名发行，已有 Worker 预检和执行适配器 | 接入生产 Worker 实际请求路径。验证并发使用同 nonce 至多一次成功、KV 丢失后无法重放，以及成员转让后的记录处理 |
| 3 · G2.4 | #210、#211 提供双路 finalized L1 证据与 OP 冻结判断 | 在转移窗口验证旧 operator 能否继续扩权；只要有延迟窗口，就记录受影响的 MANAGED 路径与剩余缺口 |
| 4 · G2.7、.9 | 原生交付草稿、resolver 观察与成员自治测试 | 由钱包持有人在测试网执行交付，第三方复核 finalized title、resolver 指针、成员独立修改与可选锁定 |
| 5 · G2.3、.8 | 已有权限负例、发行收据观察与审计材料 | 汇总 owner、proxy admin、messenger、应急权限，证明平台无法夺回已交付产权或覆写成员记录 |

最终结论逐行写回[G2 验收表](G2-ACCEPTANCE.md)，附链、区块、交易或可复核的反例。代码合并可先记入[进展记录](PROGRESS.md)。Sepolia 注册和 7702 操作涉及真实签名时，由指定钱包持有人执行。
